# js-prueffactory is TypeScript on Node 24 and ships as an npm tarball

The tool was written in Go until the cutover commit and is now TypeScript, run by Node 24 or newer. A Run spends its time in Docker containers, in `npm ci` and in the project's own tests; the host process only plans, starts containers, reads the output of JavaScript tools (ESLint, Biome, Mocha, `node:test`, Knip and others) and writes the Report. Go's speed and static binary hardly mattered for that, and a second language kept the people who use the tool every day, JavaScript and TypeScript developers, from fixing a misread tool output or adding a Check. The port changed no behaviour: the same commands, flags, exit codes, Report schema, Catalog and Benchmark profile, proven by a parity harness that ran the frozen Go build (commit `238e07f66d8cafab24ef363cb79e207bd48babd8`) and the TypeScript build on every test project, and by byte-for-byte golden Reports. The harness was deleted at the cutover.

The tool is distributed as one npm package tarball, `js-prueffactory.tgz`, with `SHA256SUMS`, in the prerelease `main-latest` (replaced on every push to `main` whose tests pass). Users install it with `npm install --global <tarball URL>`. The package holds the JavaScript emitted by the TypeScript compiler, the in-container helpers, the pinned tool configurations and data, and the Report schema, which the code reads from its own package folder. The packing step writes the commit into the package and refuses to run without one, so every Report names its build as `producer.vcs_revision`. Runtime dependencies are exactly pinned, have no native addons and no install scripts: Ajv with its formats, and nothing else from npm. YAML parsing (a port of yaml.v3, whose error texts and positions feed Findings and fingerprints) and tar writing (a port of Go's `archive/tar`) live in the repository.

Node 24 is the oldest supported major because it runs TypeScript sources without a build step during development and tests; CI runs the fast tests on Node 24 and 26, and the command exits with code 3 and a plain message on an older Node. The cost for users is that Node 24 or newer is required next to Docker; for CI jobs, the README shows a Node image with the Docker CLI added next to `docker:dind`.

## Considered options

- **Stay in Go.** Rejected: every behaviour change from the field feedback would be built in a language the team does not write daily, and the port would still be wanted later, so the changes would have been made twice.
- **Single-file executables** (Node's single executable applications or a bundler). Rejected for now: they bring back per-platform binaries and a build matrix, and the tool reads its data files from its package folder. Still possible later.
- **A container image of the tool.** Rejected: the tool drives the host's Docker daemon through the `docker` CLI and mounts no host folders, so an image would need the Docker CLI and a daemon connection inside it, which is the CI setup the README already shows with a Node image. Publishing to the npm registry or a container registry is out of scope as well; the prerelease tarball is enough.

## Consequences

- The Go answers the tests compare with are kept as JSON (`go-*.json`, `*-oracle.json`) next to the tests, and the Go programs that recorded them as plain text (`*.go.txt`). Recording an oracle again needs the Go sources of the freeze commit above: check it out and use the `.go.txt` file as a `.go` file of its package. Source comments of the form "Go: `name.go`" point to files of that commit.
- Modules that reproduce Go behaviour the Report depends on stay in the repository, in `internal/gocompat/`, `internal/yamlv3/`, `internal/jsonschema/` and `internal/tarwriter/`: JSON encoding, durations and times, flag parsing, YAML errors and positions, byte-wise sorting. Changing one of them changes the Report.
- The Go code, `go.mod`, the Go linter configuration, the Go CI jobs and the three Go binaries in `main-latest` are gone. Nothing needs a Go toolchain except recording an oracle again.
- The lock that keeps Runs from filling a shared cache volume at once (toolset, advisory database, Kubernetes schemas) is the same `flock(2)` lock as Go's on macOS only. On Linux the TypeScript build uses a lock file of its own (`<path>.owner`, created with `link(2)`, refreshed every ten seconds, broken when its holder is dead or silent for two minutes), and a Run of the old Go build is not excluded by it: both may fill the same volume. The Go build is gone from every supported setup, so this only matters for a Go Run that is still running at the time.
